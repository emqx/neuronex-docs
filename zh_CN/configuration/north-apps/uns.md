# 对接工业物联网平台（统一命名空间）

厂里上了 Ignition、Cogent DataHub 这类 IIoT 平台，或者要按 Sparkplug B 规范搭一套**统一命名空间（UNS，Unified Namespace）**时，用这一类北向应用。

## 为什么普通 MQTT 不够

MQTT 只规定了「消息发到哪个主题」，没规定「消息长什么样」。这带来三个实际问题：

- **payload 要双方事先约定**——上报格式、字段命名、数据类型都靠文档口头对齐，网关改一次格式，平台侧就要跟着改一次解析。
- **新增设备要改平台配置**——平台不知道新来的这台设备有哪些点位，需要人工在平台里建模、建标签。产线扩容时这是主要的工作量。
- **平台不知道设备是否还在线**——收不到数据，可能是设备停了，也可能是网关掉线了，或者这个点位本来就不上报。数值是新的还是十分钟前的陈旧值，平台分不清。

## Sparkplug B 怎么解决

Sparkplug B 是建立在 MQTT 3.1.1 之上的工业物联网数据传输规范，把上面三件事标准化了：

| 机制 | 解决什么 |
| --- | --- |
| **BIRTH 消息** | 设备上线时自动声明自己有哪些点位、什么数据类型、初始值是多少。平台据此自动建模，**新增设备不需要在平台侧改配置** |
| **DEATH 消息** | 通过 MQTT 遗嘱机制，网关异常掉线时 Broker 自动代发。平台立刻知道这台设备的数据不再可信，而不是继续显示陈旧值 |
| **序号与 bdSeq** | 每条消息带递增序号，平台可以发现消息丢失并请求重新 BIRTH，保证自己的模型和现场一致 |
| **别名（Alias）** | 用短整数代替点位全名传输，点位多时显著减小报文体积，省带宽 |

这几项加起来，让 MQTT 网络从「一堆主题」变成**状态可感知、结构自描述**的数据源——这正是统一命名空间的基础：全厂只有一个数据真相来源，上层各系统从这里读写，而不是两两点对点对接。

## EMQX Neuron 的映射方式

EMQX Neuron 作为 Sparkplug B 的**边缘节点（Edge Node）**接入，把每个南向驱动映射成它下面的一台设备：

```
spBv1.0 / {组 ID} / DDATA / {节点 ID} / {南向驱动名}
           ↑                  ↑            ↑
        工厂或车间          这台网关      一台设备
```

- **组 ID**：命名空间的最顶层分组，通常代表工厂或车间
- **节点 ID**：这个 EMQX Neuron 实例的唯一标识
- **南向驱动名**：一个南向驱动节点就是一台设备

打开**组 Path** 参数（默认开启）后，采集组名会作为指标名的起始路径，点位层级和现场的组织结构对得上，平台侧看到的树状结构就是产线的实际结构。

规划命名空间时，建议先定好组 ID 和节点 ID 的命名规则再批量部署——这两项写在应用配置里，改动会触发重新 BIRTH。

## 反控与生态

上层平台通过 `DCMD` 命令向指定南向驱动的点位写值，`NCMD` 用于边缘节点级命令。点位需要带 **write** 属性。

| 应用 | 什么时候用 |
| --- | --- |
| [Sparkplug B](./sparkplugb/overview.md) | 平台侧能识别 Sparkplug B 规范时优先选它。文档提供 [EMQX](./sparkplugb/sparkplug.md)、[Ignition](./sparkplugb/ignition.md)、[Cogent DataHub](./sparkplugb/cogent.md) 的实测连接示例 |

::: tip
Sparkplug B 的连接参数（服务器地址、端口、用户名密码、SSL、离线缓存）与 [MQTT 应用](./mqtt/overview.md)完全一致，只有**组 ID** 和**节点 ID** 来自 Sparkplug B 规范本身。
:::
